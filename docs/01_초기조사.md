## 4. MSG.BIN 구조 (사실 + 후보)

- 머리에 **u16 오프셋표 311개**(리틀엔디언). 첫 값 `0x026E` = 표 크기. 단조증가. 영문판은 표도 다시 썼다.
- **영문판 본문은 순수 ASCII**. 대응이 그대로 보인다:

```
0번  JP 04 02 cd 3b ff 04 00 1b 8e 1c 15 3f 0c 00
     EN 04 02 53 61 76 65 04 00 3f 0c 00          → "Save"
5번  JP 0f 89 0f 11 0a 0f 11 11 13 00
     EN 59 65 73 0a 4e 6f 00                      → "Yes
No"
```

- 제어코드(후보): `04 XX` 색·서식 · `0A` 개행 · `0F` **공백**(영문판에서 낱말 사이) · `0C` 문단 끝? · `00` 종료 · `07 06` 아이콘?
- **일본어 코드는 ASCII 가 아니다** — 전용 인코딩(1~2바이트, 미확정). 영문판이 같은 자리에 ASCII 를 넣었으므로
  «코드→글리프» 표만 확정하면 한글도 같은 방식으로 넣을 수 있다.

## 5. 글꼴 — ⛔미확정 (조사 기록)

`FONT.PXL` 65,536 B 를 다음으로 전부 그려 봤지만 **글자가 안 나온다**:
1bpp/2bpp/4bpp/8bpp × 8x8·8x12·8x16·12x12·16x16 타일, 텍스처 폭 16‥512, 칸 경계 자동 탐색(잉크 0.70 — 글꼴치곤 너무 빽빽).
엔트로피 5.86 bit/B. 첫 바이트 `00 00 40 0c 00 00 00 00 40 0c 00 00 40 0c c4 …` 는 «구조는 있는데» 글리프 격자가 아니다.
→ **압축이거나 VRAM 스위즐 배치**로 본다. `VCHAR.BIN`(엔트로피 3.83, 1bpp 잉크 0.23)도 후보.

# 2차 — 글꼴·인코딩 해독 (2026-09-21, 세이브스테이트 2장)

## 5-1. ★★★★★FONT.PXL 포맷 (사실)

세이브스테이트 VRAM 에서 **FONT.PXL 이 원본 그대로** 올라가 있는 것을 찾았다(바이트 일치).

```
VRAM (896,0)-(960,256)   ← FONT.PXL 앞 32 KB      (16비트 좌표)
VRAM (960,0)-(1024,256)  ← FONT.PXL 뒤 32 KB
VRAM (0,480)             ← FONT.CLT (팔레트)
```

- **4bpp 텍스처 · 가로 256화소(128 B/줄) · 세로 512줄**
- ★CLUT 이 「투명·흰·회·검」 **4색을 4번 반복** → **니블의 «아래 2비트»만 색을 정한다**.
  즉 실질 2bpp 안티앨리어싱 글꼴이고, **위 2비트에는 «다른 글꼴 판»이 겹쳐 들어 있다**.
  ⛔이것 때문에 1/2/4/8bpp 어떤 해석으로도 글자가 안 보였다 — 두 판이 섞여 보였던 것.
- 글리프 칸 **12×12**, 한 줄에 **21칸**(256 = 21×12 + 4). 아래판 42줄·위판 37줄 사용.

```python
rows = len(d)//128 ; b = d[:rows*128].reshape(rows,128)
v = np.empty((rows,256),np.uint8); v[:,0::2] = b & 15 ; v[:,1::2] = b >> 4
lo, hi = v & 3, (v >> 2) & 3          # 두 벌의 글꼴
```

## 5-2. ★★★★★본문 인코딩 (사실 — 실물로 검증)

**1바이트 = 1글자.** `글리프 색인 = 코드 − 0x10`.
그래서 **0x20‥0x7E 구간이 그대로 ASCII** 다(영문 패치가 글꼴을 3바이트만 바꾼 이유).

| 코드 | 뜻 |
|------|-----|
| `00` | 문자열 끝 |
| `01 XX` · `02 XX` | **한자 확장 페이지**(색인 공식 ⏳미확정) |
| `04 XX` | 서식(색?) |
| `0A` | 개행 |
| `0C` | 문단/메시지 끝 |
| `0F` | 공백 |
| `10‥FF` | 글리프 (색인 = 코드 − 0x10) |

검증한 해독:

```
CD 3B FF 1B 8E 1C 15 3F      →  セーブしますか?      (영문판 "Save?")
0F 89 0F 11 0A 0F 11 11 13   →  はい / いいえ        (영문판 "Yes
No")
MSG.BIN 0082A0:
1C 11 8E 1D 3B 9D 21 0A 02 16 8E 97 1F 11 9D AB 1C 18 AC 3B 00
  → すいませーん！⏎泊まりたいんですけどー   (실기 스샷과 일치)
```

★**한자 泊 = `02 16`** — 2바이트 코드 확인. 확장 페이지의 «색인 공식»은 아직 미확정
(아틀라스 뒷부분은 21칸/줄 격자로 안 맞는다 — 줄마다 칸 수가 다르거나 두 판이 번갈아 쓰이는 듯).

## 5-3. 화면 제약 (사용자 관찰 + 스샷)

- **대사창은 내용에 맞춰 폭·줄 수가 자동으로 늘어난다**(2줄/3줄 스샷 확인). 고정 상자 폭 제약이 약하다.

# 3차 — 코드 공식·본문 모집단 확정 (2026-09-21)

## 6-1. ★★★★★확장 코드 공식 (사실 — 실물 검증)

2바이트 코드는 «페이지»가 아니라 그냥 **16비트 값**이다.

```
글리프 색인 = (코드 − 0x10)        코드 = 1바이트(0x10‥0xFF) 또는 2바이트 빅엔디언(0x01XX‥0x03XX)
아틀라스    = FONT.PXL 의 «아래 2비트» 면 · 12×12 · 21칸/줄
```

검증: `01 C5`→所 · `01 B3`→持 · `01 5F`→金 (영문판 "GP") · `02 16`→泊 · 1바이트 `CD`→セ.
⇒ 코드 공간이 **하나로 이어진다**. 0x10‥0xFF 가 앞 240자, 그 뒤는 2바이트.

## 6-2. ★★★본문 모집단 (사실)

### MSG.BIN — 32 KB 뱅크 8개 (`tools/msg.py`)

## 7-2. ★★★화자 이름(노란 글씨)의 정체

**그래픽도 반각도 아니다 — 본문과 «같은 코드»에 서식만 다르다.**

```
04 04  C0 D3 E6  04 00      ← 「アトラ」 (MSG.BIN 안 56곳)
       ア  ト  ラ
```
`04 04` 가 «이름칸(작은 노란 글씨)» 서식, `04 00` 이 원래대로.

### 작은 글꼴 아틀라스 (실측·검증)
```
FONT.PXL y=256 부터 · 칸 8×8 · 한 줄 32칸 · 색인은 큰 글꼴과 «똑같다»
  색인 i → 행,열 = divmod(i, 32) · 좌표 = (열×8, 256 + 행×8)
  검증: 0=あ · 32=0 · 49=A · 176=ア · 195=ト · 214=ラ
글자는 색인 0‥약 280(가타카나 끝)까지만 있다. 그 뒤 y328+ 는 HUD 글꼴·아이콘·창 부품.
```

### 그래서 한글화에서 지켜야 할 것
- **이름에 쓰는 한글은 색인 0‥280 안에 넣고, 12×12(큰)·8×8(작은) 두 벌을 다 그려야 한다.**

  이름칸과 1바이트 절약을 동시에 얻는다.
- 8×8 한글은 받침까지 넣기 빡빡하다 — 이름은 짧게 짓거나 전용 8×8 글꼴을 쓴다.

# 6차 — 본문 전량 추출 (2026-09-21)

## 9-1. ⛔파서 함정 — `04 00` 의 00 은 «인자»다

문자열 끝을 「첫 0x00」으로 잡으면 `04 00`(서식 되돌리기)에서 잘린다.
그래서 「セーブ」만 잡히고 뒤의 「しますか?」가 사라졌고, 중복 판정도 엉망이었다.
`msg.scan_end()` 가 토큰 경계에서만 0x00 을 끝으로 본다(`04 XX`·`01‥03 XX` 는 2바이트).
